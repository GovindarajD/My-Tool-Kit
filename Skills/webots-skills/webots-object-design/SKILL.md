name: webots-object-design
description: Design, generate, and test a custom interactive Webots object (a console, control panel, or any prop with knobs, buttons, sliders, or a screen) natively in VRML/PROTO from a structured spec, rather than sourcing an external CAD/mesh file -- research the real object via g-query first, document the design (parts, dimensions, primitives, interactive elements, materials) before generating, generate a real labeled-screen texture with generate_faceplate_texture.py rather than a flat color, validate the generated PROTO with webots-proto-sanity-check, load it in real Webots via webots-sim-launch-debug (checking the console for structural errors) and webots-camera-vision-bridge (to see it), then run a genuine self-check loop -- compare the actual result against the reference image/description, name concrete mismatches, and iterate rather than declaring victory on the first pass. Optionally finish by building a live control console for it (Starlette + SIP + webots_bridge's generic connection layer, mirroring so-101-dual-arms/console.py). Use this whenever a user or agent needs a new physical object/prop for a Webots scene that doesn't already exist as a proven asset -- especially anything with interactive controls (a medical console, an arcade cabinet, an instrument panel) where a downloaded mesh would arrive with no physics properties and broken collision geometry anyway.

# Webots Object Design

## Why native VRML generation, not downloading a mesh

A downloaded CAD file arrives with generic origins, un-separated geometry,
and zero physics properties — and every single structural bug found while
building `so-101-dual-arms/protos/so101/So101.proto` in this same project
(a real URDF→PROTO conversion) came from exactly that category of problem:
mesh-based collision geometry causing thousands of spurious contacts,
`urdf2webots`'s box-collision flag not actually producing primitives, a
root node's own physics making the whole thing fall through the floor.
Building natively from `Box`/`Cylinder`/`Sphere` primitives sidesteps all
of it: the collision geometry IS the primitive, there's no mesh to
simplify or get wrong after the fact. This is a deliberate choice this
skill is built around (also independently confirmed via g-query research;
see `reference/knowledge/webots-simulation-pitfalls.md` items 1-3 for the
full incident history that motivates it).

## Workflow

1. **Research the real object first, via g-query.** Look up what the real
   thing actually has — controls, screen, rough dimensions, layout — before
   designing anything. Don't guess a plausible-looking layout when the real
   object's actual control set is a quick search away.
2. **Write a short design doc before generating anything**: a parts list
   (chassis geometry, each knob/button's real-world position and function,
   the screen's size) with real dimensions, not placeholder numbers. This
   is the JSON spec `scripts/generate_proto.py` consumes — writing it *is*
   the design doc, not a separate step that gets skipped.
3. **Generate the PROTO**: `python scripts/generate_proto.py spec.json --out MyObject.proto`.
4. **Validate structurally**: run `webots-proto-sanity-check` on the output
   before ever loading it — catches the same defect classes documented
   there (root physics, mesh-based collision, invalid identifiers) even
   though this generator is designed not to introduce them itself.
5. **Test for real**: load it in an actual Webots world via
   `webots-sim-launch-debug`'s `launch_with_logs.py` (with `--clear-cache`
   baked in) and read the console log — a generated PROTO that *looks*
   right can still be structurally rejected by Webots' own parser (see
   gotcha #1 below, found on the very first real test of this generator).
   Then drive each interactive element through its real extern-controller
   device (motor + position sensor) and confirm it behaves — a clean
   console log only proves the PROTO loads, not that a button doesn't
   silently drift under gravity (see gotcha #4). **Poll each device's
   sensor several times over a second or two of real elapsed simulation
   time, both at rest and after commanding it** — not one read-and-move-on
   check. A single sample cannot tell "settled" apart from "currently at
   one extreme of an ongoing oscillation" (see gotcha #4's second part);
   only a short time series can.
6. **Look at it, and actually run the self-check loop** (not a one-time
   glance): capture a screenshot via `webots-camera-vision-bridge`, then
   directly compare it against the reference image/description and name
   *specific* mismatches — material/color, missing modules (a screen, a
   distinct housing), label/icon presence, layout grouping, proportions —
   the same way a first console generated by this skill was directly
   compared against its reference photo and honestly found not to match on
   several concrete points (see "Self-check loop" below). Fix the spec and
   regenerate; don't accept the first pass as done because it loaded
   without errors. If automated screenshot capture is unavailable (a real,
   disclosed possibility — this project hit a persistent GPU rendering
   glitch in its own automated capture path more than once), fall back to
   asking a human to look at the live Webots window directly and report
   back, rather than skipping visual comparison entirely.
7. **Optionally, give it a live control console** — once the object is
   structurally and visually right, wire it up the same way
   `so-101-dual-arms/console.py` does: reuse `webots_bridge`'s generic
   `WebotsProcessManager`/`WebotsSupervisorConnection` (NOT
   `webots_bridge/service.py`'s `add_webots_instance`, which hardcodes
   e-puck-specific adapters internally — write a small per-object
   `<name>_bridge.py` with your own `CallbackAdapter`s and execution
   dispatch instead, the same way `so101_bridge` and this skill's own
   `objects/console-1/console_bridge.py` do), then a Starlette app with a
   live telemetry dashboard and `sip_execute_safe`-governed controls. This
   is what turns a static prop into something an agent can actually operate
   through SIP, not just admire.

## Real gotchas found testing the generator against a real example
   (a CT scanner console — chassis, 3 knobs, 2 buttons, a touchscreen),
   not assumed to work because the VRML looked right

1. **`SliderJoint`'s `JointParameters` has no `anchor` field at all** —
   unlike `HingeJointParameters`, which needs one. A first generated PROTO
   with an anchor on every button's JointParameters loaded with a real
   error: `Skipped unknown 'anchor' field in JointParameters node`. A
   slider's position comes entirely from its `endPoint`'s own
   `translation`; only `axis` and the stops belong in `JointParameters`.

2. **`HingeJoint` `minStop`/`maxStop` are silently ignored outside
   `(-pi, pi)`.** A first spec gave three knobs a full ±2π range (meant to
   feel like an unlimited-turn value knob); Webots loaded it with a real
   warning that the stops wouldn't be effective. For a genuinely
   continuous-turn knob, omit `min_stop`/`max_stop` from the spec entirely
   — that's a real unconstrained joint, the correct native way to model
   free rotation, not an approximation of one.

3. **Specifying `mass` alone on a `Physics` node, without `density -1`,
   triggers a real warning** (`Both 'density' and 'mass' specified: the
   'density' will be ignored`) — Webots treats an omitted `density` as
   still "specified" at its own default. Always pair `density -1` with an
   explicit `mass`, matching the convention already used correctly
   throughout `So101.proto`.

4. **A joint whose axis points along gravity, with no tuning, drifts far
   past its own defined travel range** — the same *class* of bug
   (uncommanded/undamped drift) that dominated this whole project's
   earlier debugging, showing up again in a completely different,
   from-scratch object. A first button with no spring read **0.28** on its
   position sensor — 35x past an intended 0.008m maxStop — before anyone
   had even commanded it away from rest. `springConstant 800`/
   `dampingConstant 4` (this generator's defaults) stop that gross drift.

   **A second, subtler defect hid behind that fix for an entire prior
   session, only found once a live console was watched continuously
   instead of sampled once**: a button spec's `minStop` was hardcoded to
   the exact same value as its own unpressed rest position (`0.0`) — a
   joint whose normal resting state sits *exactly on* its own hard
   mechanical limit is a classic constraint-chatter condition for any
   physics engine, independent of spring/damping tuning. It read as
   "settled" in a single earlier spot-check (a lucky single sample of an
   oscillating signal), but a continuous poll showed it oscillating
   forever between two extremes every time, on every button, whether
   commanded or left untouched. Fixed by giving `minStop` a small negative
   `stop_margin` (defaults to `min(0.001, max_travel * 0.25)`, overridable
   per-button) so the rest position sits safely *inside* the joint's range
   instead of on its boundary — confirmed to fully resolve the oscillation
   *while a button sits untouched*, using the exact same spring/damping
   constants that were unstable moments before.

   **That margin fix alone turned out not to be the whole story.** A real
   press-then-release cycle (not just sitting at rest) reintroduced the
   identical oscillation, forever, even on the margin-fixed PROTO — because
   this generator's default button spring/mass (springConstant=800,
   mass=0.02kg) gives a natural oscillation period of ≈31ms, landing almost
   exactly on Webots' **default 32ms `basicTimeStep`**: a genuine numerical
   resonance that any real velocity event re-excites, independent of the
   boundary condition the margin fix addresses. **Any world instantiating
   an object built by this generator with its default button values needs
   `basicTimeStep 8` (or smaller) in its own `WorldInfo` node** — confirmed
   directly: the identical press → over-travel → release sequence bounced
   forever at the default 32ms timestep and held perfectly flat with
   nothing else changed but adding `basicTimeStep 8`. The two fixes are
   complementary, not redundant, and only the timestep fix alone survived
   an actual press/release cycle. Full incident writeup, including why
   raising damping alone could not fix this (only shrank the amplitude):
   `reference/knowledge/webots-simulation-pitfalls.md` item 14.

   **The generalizable lesson, again — now twice over**: check every
   joint's own axis against gravity before assuming default physics
   constants are fine (the third instance of that specific lesson in this
   project's history: the SO-101's startup drift, its gripper reflex
   margin, and this button's drift). And separately: **never trust a
   single telemetry sample as proof of "settled"** — a device sensor read
   once during the self-check loop's step 5 below can coincide with either
   extreme of an ongoing oscillation by pure chance. Poll any
   gravity-aligned or spring-loaded joint's sensor several times over at
   least a second or two of real elapsed simulation time — at rest, while
   actively commanded to a target, AND after a full press-then-release
   cycle back to rest, since this exact bug held perfectly still under the
   first two checks and only appeared once something actually moved and
   released — before calling it stable. Same discipline this project's own
   pitfalls doc (item 1) already required for a whole robot's world-frame
   pose, now required one level down for a single joint's own position
   telemetry too.

## Materials and screen textures — a real, disclosed visual-fidelity gap
   found by honest comparison, not caught by any structural check

A first generated console (a CT/MRI table pendant, all primitives, zero
structural errors, fully functional) was directly compared against its
reference photo and found NOT to look similar — uniform dull gray-blue
metal instead of white/cream plastic, no distinction between generic and
"important" (confirm/mode-select) buttons, a flat dark box standing in for
a touchscreen, no labels or icons anywhere. None of this is something
`webots-proto-sanity-check` or a clean console log would ever catch —
structural correctness and visual fidelity are orthogonal, and this skill
had only ever checked the former until a human looked at the result and
said so directly.

- **Chassis material**: for a plastic housing (most consoles/panels), use a
  light, slightly warm color (`[0.93, 0.92, 0.87]`-ish) with `roughness`
  around 0.5, not a cool gray metal look, unless the reference genuinely is
  metal.
- **Button color coding**: give visually/functionally distinct buttons
  (confirm, mode-select, emergency-stop) their own accent color instead of
  leaving every button the same generic gray — a blue accent
  (`[0.13, 0.32, 0.72]`-ish) reads as "primary action" in most real
  console designs, matching this skill's own reference photos.
- **Screen content**: `scripts/generate_faceplate_texture.py` renders a
  real, readable tabbed-UI PNG (tabs + a labeled button grid) via PIL,
  applied as an `ImageTexture` on a thin Box placed just in front of the
  screen's dark bezel — because Webots' `Display` device is for LIVE,
  programmatically-drawn content and renders solid black until something
  draws to it at runtime, which looks wrong in a static scene or a
  screenshot comparison. The `Display` device is still present alongside
  the textured Box (slightly behind, same footprint) for genuine live
  content later.
- **Gotcha #5, found generating that texture**: Webots silently rescales a
  non-power-of-two texture image to the nearest power of two on load — a
  480x320 PNG was reported as rescaled to 512x512, which would visibly
  stretch/distort a rectangular UI into a square. Always choose
  `width_px`/`height_px` as powers of two (256, 512, 1024...) whose ratio
  already matches the screen's `width_m`/`height_m` ratio, so no rescale —
  and no distortion — happens at all.

## Self-check loop — a real, repeatable pattern, not a one-off manual check

This is the step that most needs discipline, because a generated object
loading cleanly and rendering *something* is easy to mistake for "done."
The actual loop, run for real building the pendant console example:

1. Generate → sanity-check → load in Webots → confirm a clean console log.
2. Capture a screenshot (or ask a human to look directly, if automated
   capture is unavailable that session) and compare it against the
   reference image/description point by point: does the chassis material
   match, are all the reference's visible modules present (a screen this
   skill initially omitted turned out to matter once a fuller reference
   photo revealed it), are buttons color-coded the way the reference
   distinguishes them, is the layout grouped the way the reference groups
   it (modular clusters vs. one flat scattered plate)?
   **Don't stop at one wide establishing shot.** A wide view of the pendant
   console looked entirely correct — right materials, right layout, right
   screen — while every knob and button on it was actually rendering
   rotated 90 degrees onto its side, invisible at that zoom level and only
   caught once a zoomed-in capture framed a single cluster of them closely
   enough to see each one's actual top face. Any part with its own
   orientation/rotation (a knob, a button, a screen panel) needs at least
   one capture close enough to judge that part's orientation specifically,
   not just the assembly's overall look.
3. **Name the mismatches out loud, specifically** — "looks nothing like
   plastic," "missing the screen module," "no labels" is the actual
   feedback that drove the materials/texture work above. A vague "looks
   okay" check doesn't catch anything a structural check wouldn't already
   catch.
4. Fix the spec (materials, add a screen, regroup the layout) and
   regenerate — this loop found real, useful defects every time it was run
   for real (the power-of-two texture bug above was found on the very
   first test of the new screen feature), not just cosmetic nitpicks.
5. Re-validate structurally AND functionally again after every visual
   change, not just visually — a texture/material change doesn't usually
   break physics, but the discipline of re-running the full check (not
   skipping straight back to "just look at it") is what catches it on the
   rare time it does.

**Updated finding, superseding an earlier "honest limitation" here**: step
2's screenshot capture depends on `webots-camera-vision-bridge`, and an
earlier pass through this project genuinely hit a persistent blank/dark
capture using `Supervisor.exportImage()` (`--viewport` mode) — at the time
that read as a general environment limitation requiring a human to look at
the live Webots window instead. Since then, confirmed directly (twice) that
a real `Camera` device on a small temporary observer robot reliably
produces a correct frame in this same environment where `--viewport`
consistently does not — see `webots-camera-vision-bridge`'s own "Self-
debugging a visual defect yourself" section for the exact pattern
(throwaway world, observer robot, keep-alive companion controller for any
other extern robot already in the world). **Prefer that pattern over asking
a human to look**, now that it's proven reliable — it's what let a knob/
button orientation bug get found and fixed without the user needing to
capture or describe anything themselves. Still true: if even the
Camera-device path somehow fails in a given session, fall back to a human
looking at the live window rather than skipping visual comparison
entirely — don't mistake "I can't get a screenshot" for "the object is
probably fine."

## If an existing asset must be imported instead of designed natively

Sometimes a suitable, simple asset genuinely already exists (a standard
component, a widely-used shape) and native generation would just be
reinventing it. If importing rather than generating:

1. Use g-query to actually find a real source — don't guess a URL.
2. Convert it the same way `so-101-dual-arms` converted its URDF
   (`urdf2webots`, or Webots' own mesh import), and immediately run
   `webots-proto-sanity-check` on the result — an imported asset is exactly
   the category of thing that produces every defect class that skill
   checks for. Treat "it imported without an error" as no signal at all
   about whether the collision geometry or root-node physics are correct.
3. Prefer this skill's own generator for anything with moving parts
   (knobs, buttons, hinges) even if the *static* body comes from an import
   — an imported mesh's joints/physics are exactly where the real bugs in
   this project's own history came from, not the static visual shell.

## Spec format and worked example

See `scripts/generate_proto.py`'s own docstring for the full JSON spec
format, and `examples/ct_scanner_console.json` /
`examples/CTScannerConsole.proto` for a complete, real, tested example (a
CT scanner operator console: desk + angled control panel chassis, three
continuous-turn knobs, a start button and an emergency-stop button, and a
touchscreen display with a bumper-type touch sensor) — generated, sanity-
checked, loaded in real Webots with a clean console log, and actuated
through its real extern-controller devices, not just written and assumed
correct.

**One disclosed limitation on the touchscreen**: the `TouchSensor` overlay
is `type "bumper"` — it reports *whether* something is touching it, not
*where* (no tap x/y coordinate). Getting an exact tap position on a
simulated touchscreen needs a Supervisor-level contact-point query, out of
scope for a single device node — documented here rather than silently
implied to work like a real touchscreen.

**A second, fuller worked example, outside this skill's own directory** —
`c:\MyWorkspace\SynapticRobots\objects\console-1\` (a real project
deliverable, not a skill-internal sample): a table-pendant controller
(joystick knob, trackball knob, 19 total interactive devices, a real
generated tabbed-UI screen texture, white/cream + blue-accent materials)
plus `console.py`/`console_bridge.py` — a full live control console for it,
built the way step 7 above describes. Went through two real rounds of the
self-check loop (uniform-gray-metal-with-no-screen → white/cream materials
+ blue accents + a real screen texture, catching the power-of-two texture
bug along the way) before being judged a reasonable match to its reference
photo. Its demo world, `pendant_controller_demo.wbt`, carries the
`basicTimeStep 8` fix from gotcha #4 above in its own `WorldInfo` node —
copy that setting into any other world that instantiates this PROTO (or
any other console built by this generator using default button values),
or its buttons will bounce forever after the first real press.
